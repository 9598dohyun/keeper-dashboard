# 전환율 진단 대시보드 기획안

작성일: 2026-08-11
대상 베이스: 리드 통합 관리 시트 (`appyHEg7jKb1Y4s4b`)
근거 데이터: 2026-06-01 ~ 08-11 인바운드 4,276건 / SKB 1,114건 (실측)

---

## 1. 배경

현행 대시보드는 "오늘 결제 ÷ 오늘 응대"로 당일 성과를 표시한다.
결과는 보이지만 어느 지점에서 전환이 깨지는지는 보이지 않는다.

실측 결과 전환 손실의 대부분이 결제 단계가 아니라 그 앞 응대 단계에서 발생한다.

- 실패사유 1위가 "콜의 늦은 대처" 49.2% (실패건 중 사유기재 1,075건 기준 529건)
- 미확정 1,674건 중 15일 이상 방치가 878건 (중복·연락금지 85건 제외 후)
- 처리 지연 15일 초과 시 전환율 7.29% (1-3시간 구간은 25.74%)

또한 유입 시간대에 따라 전환율이 크게 갈린다 (인바운드, 운영시간 평일 09-19시 기준).

| 구분 | 유입 | 비중 | 유입대비 전환율 | 15일+ 방치 |
|------|------|------|---------------|-----------|
| 운영시간(평일 09-19) | 2,040 | 47.7% | 16.52% | 18.3% |
| 영업외(평일 19-09) | 1,265 | 29.6% | 7.67% | 23.2% |
| 주말 | 971 | 22.7% | 5.25% | 26.8% |

운영시간 외 유입이 전체의 52.3%이고 전환율은 절반 이하다.
응대 체계가 다른 구간이므로 지표를 합산하면 실태가 가려진다.

따라서 이 대시보드의 목적은 성과 보고가 아니라 **방치되고 있는 리드를 찾아내는 것**이며,
모든 지표는 유입 시간대 구분을 유지한 채 표시한다.

## 2. 설계 원칙

현행 대시보드를 대체하지 않고 진단 화면을 추가한다.
`/dashboard`는 성과 보고용으로 유지하고, 신규 `/diagnosis`를 진단용으로 둔다.

| 구분 | 현행 `/dashboard` | 신규 `/diagnosis` |
|------|------------------|------------------|
| 질문 | 오늘 얼마나 땄나 | 지금 무엇이 새고 있나 |
| 날짜축 | Last Modified (당일) | 유입시간 (누적) |
| 단위 | 집계 수치 | 리드 건 단위 |
| 갱신 | 하루 1회 스냅샷 | 실시간에 가깝게 (5~15분) |

두 화면의 전환율 정의가 다르므로 같은 화면에 섞지 않는다.
`/diagnosis`에는 "이 화면은 유입 기준이며 당일 성과 지표와 분모가 다름"을 명시한다.

## 3. 참조 UI

당초 Mixpanel·GA4 차용을 검토했으나, 구현 과정에서 맞지 않는다고 판단해 방향을 바꿨다.

Mixpanel·GA4는 익명 다수의 행동 흐름을 비율로 보는 도구다. "몇 %가 이탈했나"를 알려주고
제품 개선으로 연결하는 구조다. 반면 이 대시보드가 답해야 할 질문은
"지금 누구에게 전화해야 하나"이며, 대상은 이름·번호가 있는 리드 4,276건이다.
단계도 제품 이벤트가 아니라 상담사의 수동 입력이라 자동 추적 모델이 성립하지 않는다.

따라서 실제 차용한 패턴은 다음과 같다.

| 차용 대상 | 내용 | 적용 위치 |
|-----------|------|----------|
| CRM 워크큐 (Intercom·HubSpot 계열) | 조치 대상 리드를 목록으로 쌓고 처리하게 하는 구조 | 섹션 B |
| 티켓 SLA 초과 큐 (Zendesk 계열) | 기준 시간 초과 건을 별도 구분·강조 | 섹션 B |
| 피벗 테이블 | 동일 지표를 여러 축으로 분해 | 섹션 C |

퍼널 차트는 만들지 않는다. 실측상 단계가 `유입 → 결과확정 → 결제` 3개뿐이고
중간 단계(응대 착수)는 데이터가 없어, 막대 3개짜리 퍼널은 표보다 정보량이 적다.
첫 응대 시각 데이터가 쌓여 단계가 유의미해지면 그때 재검토한다.

## 5. 섹션별 정의

### B. 방치 리드

이 대시보드의 핵심 화면이다.

대상: `[콜]최종 결과`가 비어 있는 리드. 단 `연락 금지` 또는 `전화번호 중복여부` 기재 건은 제외한다
(실측 인바운드 6~8월 기준 제외 85건 — 연락금지 0건, 중복 85건).
버킷: 유입 후 경과일 0-3 / 4-7 / 8-14 / 15-30 / 31-60 / 61일+.

15일 기준선을 두는 근거는 실측이다. 15일 초과 구간의 전환율이 7.29%로,
1-3일 구간(22.90%) 대비 3분의 1 이하로 떨어진다.

버킷 클릭 시 리드 목록을 표시한다. 표시 항목은 유입일, 경과일, 시간대, 매체, 유입페이지,
담당자, 부재중 상태, 온도감. 연락처·고객명은 표시하지 않는다.

목록은 CSV 내보내기를 지원해 문자 캠페인·재컨택 리스트로 넘길 수 있게 한다.

### C. 세그먼트 분해

**시간대별** — 유입시간(KST) 기준 3분류.

| 구분 | 판정 |
|------|------|
| 운영시간 | 평일(월~금) 09:00 ~ 18:59 |
| 영업외 | 평일 19:00 ~ 익일 08:59 |
| 주말 | 토·일 전 시간 |

운영시간은 09~19시 운영 기준이다. 변경 시 이 판정 로직을 함께 수정한다.

이 축을 상단 필터로도 제공한다. 현재 구현에서는 방치 리드 목록·버킷에 적용된다
(예: "주말" 선택 시 주말 유입 방치분만 표시). 세그먼트 표는 자체 축으로 이미 분해돼 있어 미적용.

인바운드 기준 운영시간 16.52% / 영업외 7.67% / 주말 5.25%로 차이가 크다.
SKB는 유입의 93.2%가 운영시간에 몰려 있고 시간대별 차이가 없으므로
이 축은 인바운드에만 기본 노출하고 SKB에서는 접어둔다.

**유입 출처** — 세 개 축을 탭으로 전환한다.
컬럼: 유입 / 결제 / 유입대비 전환율 / 종결대비 전환율 / 미확정률 / 15일+ 방치 / 평균경과일.

기존 지표는 `UTM_source` 우선, 없으면 `진입경로`로 하나의 채널 값을 만들었으나
두 필드는 성격이 다르므로 분리한다. 합치면 "같은 랜딩인데 매체별로 전환이 다른" 패턴이 사라진다.

| 축 | 필드 | 의미 | 채움률 |
|----|------|------|--------|
| 매체 | `UTM_source` | 광고 매체 | 82.4% |
| 유입페이지 | `진입경로` | 랜딩 유형 | 97.6% |
| 교차 | 두 필드 조합 | 매체 × 랜딩 | 둘 다 있는 건 3,507 |

`페이지경로` 필드는 인바운드 6~8월 전량 미기재(0%)라 사용하지 않는다.

**빈 값은 `(미확인)`으로 별도 구분한다.** "출처가 없다"가 아니라 "확인되지 않았다"는 뜻이며,
대표전화·지인추천처럼 추적이 붙지 않는 경로가 섞여 있다.
실제로 UTM 미확인 751건의 전환율이 19.0%로 평균보다 높은데, 이를 매체 성과로 읽으면 안 된다.
표에서 회색 배경으로 구분하고 주석을 단다.

교차 축에서 드러나는 것:

| 매체 × 유입페이지 | 유입 | 전환율 | 15일+ 방치 |
|------------------|------|--------|-----------|
| facebook.business × 견적계산기 | 956 | 5.9% | 235 |
| naver × 견적계산기 | 387 | 11.1% | 89 |
| facebook.business × 매장보안_페이지 | 251 | 4.4% | 92 |
| naver × 도입문의 | 210 | 22.9% | 40 |

같은 견적계산기라도 facebook 5.9% / naver 11.1%로 두 배 차이가 난다.
랜딩 문제가 아니라 매체 문제라는 뜻이며, 합쳐서 보면 이 구분이 불가능하다.
`facebook.business × 견적계산기` 조합 하나가 유입의 22%를 차지하며 단일 손실원으로 가장 크다.
`매장보안_페이지`는 미확정률 68.9%로 사실상 처리가 안 되고 있다.

**담당자별** — `[콜]담당자` 기준. `(미배정)` 별도 행.
컬럼: 배정 / 결제 / 전환율 / 미확정 / 평균 경과일.

물량과 전환율을 함께 보여 부하 불균형을 확인한다.
인바운드 기준 김수정 2,521건 8.4%, 구태진 1,396건 19.0%로 물량이 많은 쪽 전환율이 낮다.

### D. 응대 속도

`유입시간` → `첫응대시각` 간격. 버킷은 0-30분 / 30분-1h / 1-3h / 3-12h / 12-24h / 1일+.

반드시 두 계열로 분리한다.

- 신규 유입분: 유입일과 첫응대일이 같은 날 또는 익일
- 적체 소화분: 그 이전 유입분을 뒤늦게 응대한 건

분리하지 않으면 적체 소화분이 평균을 왜곡한다.
2026-08-11 확인 기준 인바운드에 유입 06-30 / 첫응대 08-11 = 경과 1,007시간 건이 존재한다.

데이터 축적 전까지 이 섹션은 "집계 중 (2026-08-11~)"으로 표시한다.

### E. 실패사유

`실패사유` 기재 건 기준 가로 바. 상단에 기재율을 병기한다
(인바운드 실패 1,492건 중 1,075건 기재 = 72.1%).

실패건 = 최종결과가 기재됐고 결제완료·중복문의·B2B가 아닌 건.
`실패사유` 값이 있어도 최종결과가 결제완료·중복문의·미확정인 41건은 제외한다
(결과가 나중에 바뀌며 남은 잔여값).

기재율을 함께 보여주지 않으면 미기재분이 가려진다.

## 6. 지표 정의

| 지표 | 계산 | 날짜 기준 |
|------|------|----------|
| 유입 | `유입시간`이 기간 내 | 유입시간 |
| 결제 | `[콜]최종 결과` = `결제 완료*` | 유입시간 |
| 유입대비 전환율 | 결제 ÷ 유입 × 100 | 유입시간 |
| 종결대비 전환율 | 결제 ÷ 결과기재 × 100 | 유입시간 |
| 미확정 | `[콜]최종 결과` 빈값 | 유입시간 |
| 경과일 | 오늘 − 유입일 (미확정 건만) | 유입시간 |
| 리드타임 | `첫응대시각` − `유입시간` | 유입시간 |
| 유입 시간대 | 평일 09-19 운영시간 / 평일 19-09 영업외 / 토·일 주말 | 유입시간(KST) |

전환율은 두 가지를 항상 함께 표시한다.
미확정 비중이 인바운드 39.1%, SKB 50.0%로 높아 한쪽만 보면 판단이 왜곡된다.

## 7. 구현

기존 코드를 건드리지 않고 병렬 추가한다.

```
src/lib/metrics3/          진단 지표 엔진 (신설, metrics·metrics2는 미변경)
  types.ts                 타입 정의
  compute.ts               방치·세그먼트·리드타임·실패사유 산출
  stale.ts                 방치 판정 + 경과일 버킷 (15일 기준선 상수화)
  time-segment.ts          유입 시간대 판정 (운영시간 09-19 상수화)
  source.ts                매체·유입페이지 분해 + (미확인) 처리
src/app/api/diagnosis/     GET /api/diagnosis?range=30|60|90
src/app/diagnosis/         화면
src/app/components/
  diagnosis.tsx            메인 (필터·섹션 조합)
  stale-leads.tsx          섹션 B
  segment-table.tsx        섹션 C
  leadtime-chart.tsx       섹션 D
scripts/compute-diagnosis.ts   지표 계산 → KV (d3:range:30|60|90, d3:latest)
```

구현 완료 (2026-08-11). `npx tsc --noEmit` + `npm run build` 통과.
엔진 산출값이 Python 실측과 일치하는지 대조 확인함
(유입 4,276 / 결제 485 / 시간대별 16.5·7.7·5.3% / 방치 878 / 제외 85).

데이터 수집은 기존 `scripts/fetch-airtable.ts`를 확장한다.
추가로 가져오는 필드는 `첫응대시각`, `실패사유`, `[콜]부재중 상태`, `전화번호 중복여부`,
`연락 금지`, `[콜]온도감`(인바운드만). v2는 기존 필드만 읽으므로 영향 없다.

개인정보(고객명·연락처)는 기존 원칙대로 수집·노출하지 않는다.
리드 목록은 레코드 ID만 보유하고, 상세 확인은 에어테이블 인터페이스로 링크한다.

갱신 주기는 방치 리드 판정이 목적이므로 하루 1회로는 부족하다.
GitHub Actions cron을 1시간 간격으로 조정하거나, 조회 시점 계산 방식을 검토한다.
단 Vercel Hobby 10초 제한이 있어 KV 캐시 경유는 유지한다.

## 8. 단계별 적용

| 단계 | 범위 | 선행 조건 |
|------|------|----------|
| 1차 | 섹션 B(방치 리드) + C(세그먼트) + E(실패사유) | 완료 (2026-08-11) |
| 2차 | 섹션 D(응대 속도) 실측 반영 | 첫응대시각 2주 이상 축적 (8월 하순) |
| 3차 | 퍼널 재검토 | 응대 착수 단계가 유의미해진 뒤 |

1차를 우선하는 이유는 방치 878건이 지금 조치 가능한 물량이기 때문이다.
화면이 없어도 리스트 추출만으로 즉시 액션이 가능하므로, 1차 구현 전에
CSV 추출을 먼저 실행하는 것도 검토할 수 있다.

## 9. 확인 필요 사항

- 갱신 주기를 1시간으로 올릴 경우 Airtable API 호출량 검토 필요
  (인바운드 11,276건 전수 fetch 기준 약 113회 호출, rate limit 5req/s)
- 방치 제외 조건은 `연락 금지` + `전화번호 중복여부` 기재로 확정했다.
  `[콜]必팔로우업 예정 날짜`는 6~8월 미확정 건 중 기재가 0건이라 제외 조건에서 뺐다.
  향후 이 필드를 쓰기 시작하면 "예정일이 미래인 건"을 제외 대상에 추가할 것
- 담당자별 리드 품질이 균등 배분되는지 확인되지 않아, 전환율 차이를 역량으로 해석할 수 없음.
  배분 규칙 확인 후 지표 해석 기준을 정할 것
- 섹션 B 리드 목록의 에어테이블 인터페이스 링크 URL 확보 필요
